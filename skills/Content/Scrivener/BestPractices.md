# Lightweight Scrivener Organization

Doctrine: **maximize value, minimize structure.** Every organizational mechanism must earn its place; the default answer to "should we add structure?" is no. An empty label axis costs nothing; a half-maintained one costs trust in every view that uses it.

## The Four Mechanisms, One Job Each

| Mechanism | Cardinality | Use for | Don't use for |
|-----------|-------------|---------|---------------|
| **Binder folders** | tree | Acts/chapters/parts — the compile skeleton | Thematic grouping (that's keywords/collections) |
| **Labels** (renamable axis) | one per doc | ONE static trait: POV, storyline, or location — pick a single axis per project | Progress tracking |
| **Status** | one per doc | Revision stage (e.g. draft → revise → done) | Content traits |
| **Keywords** | many per doc | Cross-cutting tags (characters present, themes) — only when one label axis stops being enough | Anything a label already covers |

**Collections** (incl. saved-search collections) give alternate views without touching binder order — reach for them before reorganizing the binder itself.

## Jm's Existing Conventions (observed, preserve them)

Verified 2026-08-14 in the On Set project — Jm already follows the one-axis pattern:

- **Label axis renamed to "POV"** with character values (Emi, Leo, …) plus color names
- **Status as revision verbs:** diagnose / keep / revise / rewrite
- **Numbered chapter folders** in the Draft folder: `1. Onset`, `2. The New World`, …
- **A rich custom-metadata scene grid:** goal / conflict / outcome / value shift / link (Therefore/But/And-then) / setting / cast / plot-character-world-emotion checkboxes

When auditing or restructuring **any** Jm project, these conventions are the house style. Extend them; do not replace them with a different scheme. The scene grid especially is craft infrastructure (scene-sequel discipline) — never flatten or "simplify" it away.

## Audit Heuristics

Signals worth flagging in an Organize audit (each is a question for Jm, not an automatic fix):

1. **Placeholder titles** — documents named "Scene" say nothing on the corkboard; suggest titling from the synopsis or first line.
2. **Empty synopses** on manuscript documents — the corkboard/outliner is blind without them.
3. **Unused axes** — a label/status axis with defined values but few assignments is either abandoned (remove values) or aspirational (backfill only if Jm wants the view it enables).
4. **Compile-inclusion drift** — non-manuscript material inside the Draft folder, or manuscript scenes excluded from compile without an evident reason.
5. **Trash buildup** — items in Trash are one "Empty Trash" from gone; anything worth keeping should move to Research.
6. **Orphan Data dirs** (`Inspect.ts --check`) — usually harmless remnants, but list them.
7. **Deep nesting** — more than folder → subfolder → document in the Draft folder is usually structure for its own sake.

## What "Organized" Means Here

A project is organized when: the binder tree mirrors the compile output; every manuscript document has a title that means something on a corkboard card; one glance at label color + status tells Jm where the work is; and nothing else is asked of the system. Anything beyond that must justify itself against the cost of maintaining it.
